一句話結論

user 原始問題：「不同家族寫實作跟測試」vs「EP 先寫測試規劃」——三方收斂：兩者互補，且嚴格分先後。
第一層：EP 測試契約（先做、全量）

top-level「測試規劃」段放在實作段落前面——TC（claim／Given/When／oracle／oracle_source／evidence class）在任何人寫實作碼之前凍結。oracle 獨立性由「EP 作者（GLM）↔ 實作者（Muse）本來就跨家族」兌現。

第二層：判讀邊界獨立（高風險段）

兩道便宜防線：pre-RED challenge（跨家族 blind derive 審 oracle＋抓漏場景）＋ code-review 架構軸（整體測試邏輯 vs diff 結構）。same-writer RED 的風險改由「凍結 oracle＋RED provenance＋digest 凍結＋架構審查」管理。

設計原則（codex r3 定調）

Family separation 放在 judgment boundary，不放在 every authorship boundary——獨立性買在「審規格」（challenge）與「審結構」（review），不買在「把 oracle 抄成 pytest」（翻譯≈機械，誰翻都一樣）。

第三家族寫手＝P0 最後手段（非高風險預設）：啟用條件預寫死——MVP fault-injection 證明 challenge＋review 擋不住 fixture fidelity 級穿透才啟用。原本「Codex 寫 RED」的三家族方案在 r3 被兩家共同降階：oracle 凍結後翻譯者是谁近乎不重要。

決策鏈：user 提案（家族分離 vs EP 測試規劃段）→ 三方初輪（契約先/分離後）→ user 澄清（top-level、實作前）→ 融合版＋implement 拆段追問 → 本頁定案。

核心流程

高風險段的完整 TDD 管線（低風險段＝左上分支，維持現行 same-writer TDD 不變）。
v3.1 定案管線：契約凍結 → challenge → same-writer RED（三 gate＋digest 凍結）→ GREEN → 機械審計 → 架構審查 → judge
  • 五個絕不外派點（主 session full）：階段 0 風險分級、canonical TC 語義變更、RED 語義 gate、contract-gap 裁定、完成報告最終驗收宣稱——「這些不是執行工作，是在決定什麼算正確」。
  • RED provenance 三栓（r3 共識，防 test-after 劇場化與 silent mutation）：① RED receipt（TC-ID＋production baseline 身份＋contract-test digest＋failing predicate——落檔存證非中途 git commit，implement 禁中途 commit 不變）；② RED 過 gate 後 contract-test digest 凍結——GREEN/REFACTOR 不得靜默改 frozen test，要改必經 mutation authority gate；③ 基線跑法——新測試跑在 pre-change baseline 上必須紅（在 baseline 綠＝vacuous，直接退回）。
  • 「實作現況」禁作契約證據：amendment 只接受獨立源（domain invariant／reference truth／differential／metamorphic／real fixture 行為）；fix-test Type B/E（涉 expected 語義）＝TC escalation signal，不直接改測試。
讀圖須知：圖的不變項是角色結構——EP/TC 作者、challenge（advisory）、實作者（單一 model）、機械審計、架構審查、judge。節點上標的家族是現值舉例；家族→model 解析單一源＝model-routing，workflow 檔只寫角色/profile 詞彙、不綁家族。

節點色＝現值舉例（紫=GLM full／藍=GLM lite 機械／綠=跨家族 advisory／琥珀=實作家族）。低風險分支照樣走凍結 TC 的 same-writer TDD——分離只買在判讀邊界。

成本防線（cache 顧慮 → 設計內建）

  • 觸發即節流：classifier 命中才拆（會計總量／風控 sizing／持久化寫路徑／跨 context 接線／時間語義／公開 API／silent-corruption）——量少是設計的一部分。
  • Test Context Pack：階段 1 預生成 compact 慣例包（fixture/conftest/marker/介面面/real-fake 邊界），所有 test writer 重用——省的正是重複掃 repo 的 cache miss。
  • 輸入 hard cap＋session resume：RED 工單輸入包寫死上限；collision 退回走 --session-id 續用原 context（迴圈內 cache 保住）。
  • 量測入 MVP：額度消耗實測為收斂訊號——稅太重則降級「只 P0 invariant 面啟用」或停在契約層。
成本量級（兩家共識的誠實版）：每拆一段 ≈ 多一個中小型 implementation subtask（RED 工單 0.5–1× 該段 GREEN——結構推估無實測）；昂貴的不是 pytest 幾行，是第二家族重建 testing conventions／fixture topology／public surface。RED 外派永遠更貴——買的是獨立性，不是省錢。真正適合外派省 token 的是機械腿（驗證執行／對帳／review evidence＝lite）。

MVP（seeded fault-injection，不跑 live——~3 agent call 量級）

  1. 挑一段已完成的歷史高風險碼（有 frozen TC 最好；沒有補 3–5 條迷你 TC）
  2. Lane A（考 challenge）：4 clean＋4 oracle mutant（sign/方向、單位、邊界、漏 invariant 項）——各走 blind-derive→reveal protocol
  3. Lane B（考 audit＋review）：六類 test 架構 mutant（只 unit 無 integration／mock 掉 real boundary／fixture 拿掉關鍵性質／expected 吃 production helper／symbol 有 hit 但 consumer path 未走／RED 後偷改斷言）
  4. 量：recall＋誤報率＋attribution accuracy（不只說可疑、要指出正確 predicate）＋defect routing correctness（機械軸→audit、結構判斷→review、oracle→challenge，各司其職）
  5. 過線標準預凍結（判分條件先寫死再看輸出——instruction-testing 原則）：例 challenge ≥3/4 且誤報 ≤1；review 至少多抓 1 個機械抓不到的，否則軸B 重設計
  • 誠實邊界：fault-injection 量的是「防線對已知壞樣的靈敏度」，非「對未知 oracle 錯的靈敏度」——過了 MVP 只證明防線不是擺設，不證明 production 有效。個位數樣本只判 discriminating power。
  • 啟用第三家族的實證條件：MVP 顯示 fixture fidelity／shared assumption／silent test mutation 仍大量穿透 → 「第三家族 RED author」升回 P0 fallback；否則不付常態成本。

AIR-70 關係

本設計仍解 `impl/test-gen` 幽靈角色——但 r3 後答案反轉：test-gen 不必成為常設角色（lifecycle 缺 stage 的解法＝test 的獨立性由 oracle 層＋review 層分擔），僅以「P0 最後手段＋預寫死的啟用條件」入 lifecycle 表。AIR-70 的一致性修復照舊範圍結案，本弧結論 materialize 回其一項。
